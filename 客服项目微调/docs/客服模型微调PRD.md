## 2. 背景与目标

### 2.1 现状

现有客服系统 [app/services/chat.py](../app/services/chat.py) 的完整链路是一条：

```
POST /api/chat
  → services/chat.py.handle_message
  → services/faq.py.search（2-gram 重合度检索 top-3 FAQ）
  → SYSTEM_PROMPT + 检索结果 + 本轮用户消息
  → services/llm.py.generate（通用 deepseek-chat 单轮调用）
```

意图识别、槽位抽取、澄清、流程控制、人工升级 **全部塞进一段 `SYSTEM_PROMPT` 让模型自由发挥**，没有任何结构化约束：

- 无意图枚举、无槽位状态、无流程状态机、无结构化输出。
- 历史消息不喂给模型（`chat.py` 只发 `system` + 本轮 `user` 两条），多轮追问必然答歪。
- 检索是 2 字 bigram 重合度，无分词、无向量、全表扫；单字查询必 miss，英文 `APP` 与库中 `App` 大小写差异也 miss。
- 人工升级只靠提示词「引导用户联系人工客服」，没有把已确认的意图/槽位/历史转给人工的机制。

### 2.2 微调目标

把 [项目实战.md](../项目实战.md) 4.3 节的五类能力，做成 **结构化、可评估、可集成进现有服务** 的闭环，替代当前「提示词自由发挥」的现状。

| 4.3 小节 | 能力 | 落地目标 |
|---|---|---|
| 4.3.1 | 用户意图识别 | 输出受控意图枚举，支持多意图、模糊意图 |
| 4.3.2 | 槽位信息抽取 | 输出结构化槽位，识别缺失/冲突/非法 |
| 4.3.3 | 澄清问题生成 | 在槽位缺失或多意图时生成具体澄清问题 |
| 4.3.4 | 多轮流程状态管理 | 按状态机推进流程，保持上下文，不重复询问 |
| 4.3.5 | 异常处理与人工升级 | 异常时兜底或转人工，不错误承诺，保留上下文 |

## 3. 需求范围

### 3.1 In-scope

- 意图识别、槽位抽取、澄清生成、多轮流程状态、异常与人工升级五类能力。
- 训练数据构建、微调、评估。
- 运行时集成：改造现有 FastAPI 客服，接入微调模型的结构化输出与对话状态。

### 3.2 Out-scope

- 不重写 [app/services/faq.py](../app/services/faq.py) 的检索算法本体（升级属可选，见 §8）。
- 不替代人工客服，不改变听书业务本身（会员/播放/下载等规则以知识库为准）。
- 不新增对外业务接口，不改 `POST /api/chat` 的对外契约（响应字段扩展见 §9）。

## 4. 现状与差距分析

### 4.1 架构现状

- 入口：[app/routers/chat.py](../app/routers/chat.py) `POST /api/chat`，请求 [app/schemas.py](../app/schemas.py) `ChatRequest{message, conversation_id?}`，响应 `ChatResponse{reply, conversation_id}`。
- 数据：[app/models.py](../app/models.py) 仅 `FAQ` / `Conversation` / `Message` 三表。
- 检索：[app/services/faq.py](../app/services/faq.py) 2-gram 重合度，`search()` 返回 top-3 FAQ。
- 生成：[app/services/llm.py](../app/services/llm.py) 单轮 `chat.completions.create`，`temperature=0.3`。
- 评测：[eval/评测集.jsonl](../eval/评测集.jsonl) 68 条 / 10 类，[eval/打分表.md](../eval/打分表.md) D1–D5 五维 + Go/No-Go。

### 4.2 差距表

| 4.3 能力 | 现状 | 需新增 |
|---|---|---|
| 意图识别（4.3.1） | 无枚举，靠提示词猜 | 意图枚举 + 结构化输出 + 多意图/模糊处理 |
| 槽位抽取（4.3.2） | 无槽位概念，订单号等混在文本里 | 槽位枚举 + 结构化提取 + 缺失/冲突/非法判定 |
| 澄清生成（4.3.3） | 模型自由追问，可能一次问一串 | 澄清触发条件 + 一次一问话术 |
| 多轮流程状态（4.3.4） | `Conversation` 表只存不用，历史不喂模型 | 对话状态/槽位状态机 + 历史消息喂入 |
| 异常与人工升级（4.3.5） | 仅提示词「引导联系人工」，无上下文打包 | 升级判定 + 兜底话术 + 上下文打包给人工 |

### 4.3 已知缺陷（来自 [tests/test_chat_api.py](../tests/test_chat_api.py) `@unittest.expectedFailure`）

- 历史消息不发送给 LLM（`test_previous_turns_are_sent_to_llm`）。
- 空 `message` / 纯空白未在 schema 层拦截，白烧一次 LLM 调用（`test_empty_message_is_rejected`）。
- LLM 异常直接 500，且 user 消息未 flush/commit 随回滚丢失（`test_llm_failure_is_handled_gracefully`）。
- 未知 `conversation_id` 静默新建同 id 会话（`test_unknown_conversation_id_is_created`）。

这些缺陷与 4.3.4、4.3.5 直接相关，运行时集成必须一并修复。

## 5. 功能需求

每项能力按「能力定义 / 输入输出 / 正例与反例 / 边界与异常」四要素描述。结构化输出字段的完整定义见 §6。

### FR1 用户意图识别（4.3.1）

- **能力定义**：识别用户消息对应的业务意图，输出受控意图枚举；支持多意图（一条消息含多个诉求）和模糊意图（诉求不清）。
- **意图枚举**：

| 意图 | 说明 |
|---|---|
| `查询订单` | 查订单状态、物流、到账 |
| `修改信息` | 改绑手机号、改会员信息、取消自动续费 |
| `申请退款` | 退款、退订 |
| `投诉升级` | 投诉主播/内容、情绪强烈 |
| `人工转接` | 明确要求找人工 |
| `FAQ 咨询` | 知识库可覆盖的常见问题 |
| `超范围` | 与听书业务无关（天气、写代码、炒股） |
| `闲聊` | 寒暄、情绪倾诉 |

- **输入输出**：输入当前轮用户消息 + 可选历史；输出 `intent`（单个或多个）。
- **正例**：
  - 「会员怎么续费？」→ `intent: ["FAQ 咨询"]`
  - 「订单号 20250101001，钱扣了会员没到账」→ `intent: ["查询订单"]`
  - 「我要退款，还要投诉你们」→ `intent: ["申请退款", "投诉升级"]`（多意图）
- **反例**：不能把「今天天气怎么样」判成任何业务意图，应判 `超范围`。
- **边界与异常**：模糊意图（「这个不行」）不能硬猜，交澄清或人工；多意图按优先级或逐个处理，不能只答一个丢另一个。

### FR2 槽位信息抽取（4.3.2）

- **能力定义**：从用户消息中抽取关键槽位。
- **槽位枚举**：

| 槽位 | 说明 |
|---|---|
| `订单号` | 订单/交易编号 |
| `手机号` | 联系/绑定手机号 |
| `商品名` | 节目、专辑名 |
| `时间` | 事发/购买时间 |
| `地址` | 收货/退款地址 |
| `金额` | 涉及金额 |
| `问题类型` | 问题分类（充值/播放/退款等） |

- **输入输出**：输入消息；输出 `slots`（键值对，缺的槽位不出现或标记 `null`）。
- **正例**：
  - 「订单号 20250101001 支付成功但没到账」→ `slots: {订单号: "20250101001", 问题类型: "充值未到账"}`
- **反例**：不要把「会员怎么续费」里的「会员」误抽成 `商品名`。
- **边界与异常**：识别缺失槽位（无订单号）、冲突槽位（订单号前后不一致）、非法值（手机号位数不对），这三类都要触发 FR3 澄清或 FR5 升级。

### FR3 澄清问题生成（4.3.3）

- **能力定义**：当诉求不清、槽位缺失、或多个流程都可能匹配时，提出具体的澄清问题。
- **输入输出**：输入当前意图 + 已收集槽位；输出 `next_action: "clarify"` + `reply`（澄清话术）。
- **触发条件**：意图模糊；关键槽位缺失（如申请退款缺 `订单号`）；多个流程可能匹配。
- **话术规范**：一次只问一个关键缺失项；具体（问「请提供订单号」，不问「请补充信息」）；不重复询问已确认项。
- **正例**：
  - 意图 `申请退款`、无 `订单号` → 「请提供您的订单号，我帮您查询。」
- **反例**：一次性追问「请提供订单号、手机号、商品名、金额」，属不合格话术。

### FR4 多轮流程状态管理（4.3.4）

- **能力定义**：根据当前流程、已收集槽位和用户补充信息决定下一步动作。
- **状态机**：

```
意图识别 → 槽位收集 → 澄清 → 执行 → 结束
              ↑         │
              └─────────┘（用户补充后回到槽位收集）
```

- **输入输出**：输入当前流程状态 + 已收集槽位 + 本轮消息；输出 `next_action`（`collect_slot` / `clarify` / `execute` / `handoff` / `done`）。
- **规则**：正确跳转流程；保持上下文；不重复询问已提供信息；已确认的槽位不再覆盖。
- **正例**：
  - 第 1 轮「会员怎么续费？」→ `FAQ 咨询`，直接 `execute`。
  - 第 2 轮「那取消的话呢？」→ 承接上文，答取消自动续费，不重述续费路径。
- **反例**：第二轮把「那怎么取消？」答成第一轮续费流程（对应现有 `test_previous_turns_are_sent_to_llm` 缺陷）。

### FR5 异常处理与人工升级（4.3.5）

- **能力定义**：识别情绪升级、规则不可处理、信息冲突、流程无法继续等情况，进入兜底或人工流程。
- **触发条件**：

| 触发 | 说明 |
|---|---|
| 情绪升级 | 「再解决不了我就去 12315 投诉」 |
| 规则不可处理 | 知识库无此规则（学生优惠、导出 MP3） |
| 信息冲突 | 用户两次给的订单号不一致 |
| 流程死路 | 澄清多次仍无法推进 |

- **输入输出**：输出 `handoff: true` + `reply`（人工引导话术）+ 上下文打包（见 §8）。
- **规则**：及时升级不硬答；不错误承诺（不承诺退款金额/时效）；保留已确认意图、槽位、历史给人工，避免用户重复描述。
- **正例**：
  - 「订单号 20250101001 支付成功但没到账」→ 需人工核对，`handoff: true`，回复引导 + 打包订单号。
- **反例**：对「年费会员支持退款吗」承诺「一定退款」或编造退款比例（对应 [eval/评测集.jsonl](../eval/评测集.jsonl) M-06 的 `must_not`）。

## 6. 结构化输出协议

微调模型对每轮输出一个 JSON 对象（替代当前的纯文本回复）：

```json
{
  "intent": ["申请退款"],
  "slots": {"订单号": "20250101001", "金额": null},
  "next_action": "collect_slot",
  "reply": "请提供您的订单号，我帮您查询。",
  "handoff": false
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `intent` | string[] | 意图枚举，见 FR1；可为空数组表示未识别 |
| `slots` | object | 槽位键值对，见 FR2；缺失槽位可不出现或为 `null` |
| `next_action` | string | `collect_slot` / `clarify` / `execute` / `handoff` / `done` 之一 |
| `reply` | string | 面向用户的中文回复 |
| `handoff` | bool | 是否转人工 |

约束：

- JSON 解析失败时，服务端回退为纯文本模式（直接展示 `reply` 或转人工），不 500。
- `handoff: true` 时，服务端把当前意图、槽位、历史消息打包进转人工上下文（§8）。
- `reply` 是唯一对外展示字段，`intent`/`slots`/`next_action` 用于内部流程，不直接展示。

## 7. 训练数据需求

训练数据逐项对齐 [项目实战.md](../项目实战.md) 4.3「训练数据」原文。标注统一输出为 §6 的 JSON。

### 7.1 意图识别（4.3.1）

- 数据类型：用户原始消息 + 意图标签（§FR1 枚举）+ 多意图样例 + 相似意图区分样例。
- 标注 schema：`{"text": "...", "intent": ["..."]}`。
- 来源：`eval/评测集.jsonl` 的 `cat`（会员/播放/下载/账号/售后/超范围/对抗/多轮/错别字/情绪）+ 业务补充。
- 反例：`超范围` 类 8 条、`对抗` 类 8 条全部入集，训练「不答不该答的」。

### 7.2 槽位抽取（4.3.2）

- 数据类型：用户消息 + 槽位标注 + 缺失槽位样例 + 错误槽位反例。
- 标注 schema：`{"text": "...", "slots": {"订单号": "...", ...}}`。
- 来源：含 `订单号` 的用例（M-04、S-05）扩展，覆盖 `手机号`/`商品名`/`时间`/`地址`/`金额`/`问题类型`。
- 反例：不含槽位的 FAQ 消息，训练输出空 `slots`。

### 7.3 澄清生成（4.3.3）

- 数据类型：模糊用户消息 + 缺失槽位状态 + 标准澄清话术。
- 标注 schema：`{"text": "...", "intent": "...", "slots": {...}, "reply": "请提供订单号"}`。
- 来源：多轮类（T-02、T-05）中第二轮信息不足的样本，补标准澄清话术。
- 反例：一次多问、问已确认项的话术标注为负样本。

### 7.4 多轮流程状态（4.3.4）

- 数据类型：多轮对话 + 流程节点 + 槽位状态 + 下一步动作标注。
- 标注 schema：每轮 `{"intent", "slots", "next_action", "reply"}` 序列。
- 来源：`eval/评测集.jsonl` `多轮` 类 6 条 + 自建多轮流程样例。
- 反例：重复询问已提供信息、跳错流程的对话。

### 7.5 异常与人工升级（4.3.5）

- 数据类型：异常对话 + 信息冲突样例 + 投诉升级样例 + 人工转接样例。
- 标注 schema：`{"text": "...", "handoff": true, "reply": "..."}`。
- 来源：`情绪` 类 4 条、`投诉/对抗` 类、`超范围` 类。
- 反例：硬答、错误承诺（编造退款比例/电话/时效）的回复标注为负样本。

## 8. 运行时集成方案

改造现有 [app/](../app/) 代码，接入微调模型。

1. **历史消息喂入**：`handle_message` 带 `conversation_id` 时，从 [app/models.py](../app/models.py) 读 `Message` 历史，连同本轮拼成 messages 喂给模型（修复 `test_previous_turns_are_sent_to_llm`）。
2. **结构化输出**：`llm.generate` 增加 `response_format` 或提示词约束输出 JSON；新增解析层，解析 §6 JSON，失败回退纯文本/人工，不 500。
3. **对话状态持久化**：新增会话状态/槽位表（见 §9），每轮把 `intent`、`slots`、`next_action` 落库，支撑多轮流程状态机。
4. **检索升级取舍**：当前 2-gram 检索可保留（轻量）或升级为向量/分词（准确率更高）；PRD 建议先保留，槽位/意图信息已由微调模型提供，检索仅作 FAQ 知识补充。
5. **人工转接上下文打包**：`handoff: true` 时，把已确认意图、槽位、最近 N 轮历史打包成结构化上下文，随会话落库供人工客服读取，避免用户重复描述。
6. **入参校验**：`ChatRequest.message` 加 `min_length` 校验拒绝空串/纯空白（修复 `test_empty_message_is_rejected`）。
7. **LLM 异常兜底**：`generate` 抛异常时返回友好提示 + 保留 user 消息落库（修复 `test_llm_failure_is_handled_gracefully`）。

## 9. 接口与数据模型变更

### 9.1 请求/响应（[app/schemas.py](../app/schemas.py)）

- `ChatRequest.message`：加非空校验（`min_length=1` + 去空白后非空）。
- `ChatResponse`：可选新增 `intent`、`handoff` 字段（对外契约保持 `reply` + `conversation_id` 不变，新增字段向后兼容）。

### 9.2 数据表（[app/models.py](../app/models.py)）

现有 `FAQ` / `Conversation` / `Message` 三表基础上，新增：

- `DialogueState`：`id`、`conversation_id`、`intent_json`、`slots_json`、`next_action`、`updated_at` —— 每会话一条当前流程状态。
- `HandoffContext`（可选，或并入 `DialogueState`）：`conversation_id`、`summary_json`、`created_at` —— 转人工时的上下文快照。

字段名与现有模型风格（`Mapped` + `mapped_column`）保持一致；只新增，不改动现有 `FAQ`/`Conversation`/`Message` 结构。

## 10. 评估方案

### 10.1 复用现有评测

- 数据集：[eval/评测集.jsonl](../eval/评测集.jsonl) 68 条 / 10 类。
- 打分：[eval/打分表.md](../eval/打分表.md) D1–D5 五维 + Go/No-Go（编造率 0、`handoff=true` 用例 D3≥1 比例 100%、加权总分 ≥85%）。
- 跑批：[eval/run_eval.py](../eval/run_eval.py)，自动初筛 `points` 命中与 `must_not` 泄漏，落 `eval/result.csv`。

### 10.2 每项能力专项指标

| 能力 | 指标 |
|---|---|
| 意图识别 | 意图分类准确率；多意图/模糊意图召回 |
| 槽位抽取 | 槽位 F1；缺失/冲突识别准确率 |
| 澄清生成 | 一次命中率（澄清后用户补全目标槽位的比例）；问题具体性 |
| 多轮流程状态 | 流程跳转正确率；重复询问率 |
| 异常与人工升级 | 升级及时率；错误承诺率（应趋近 0） |

### 10.3 扩充思路

针对 4.3 五类能力，在现有评测集外补：多轮流程样例、槽位抽取样例、澄清对话样例、升级样例；每条同样带 `points`/`must_not`/`handoff` 三元组。

## 11. 验收标准

逐条对齐 [项目实战.md](../项目实战.md) 4.3「评估重点」：

1. 意图分类准确，能识别多意图和模糊意图（4.3.1）。
2. 槽位完整、准确，能识别缺失和冲突信息（4.3.2）。
3. 澄清问题必要、具体、一次只问关键缺失项（4.3.3）。
4. 流程跳转正确，保持上下文，不重复询问已提供信息（4.3.4）。
5. 及时升级，不错误承诺，保留必要上下文给人工客服（4.3.5）。
6. 通过 [eval/打分表.md](../eval/打分表.md) 的 Go/No-Go：编造率 0、`handoff=true` 用例 100% 给人工入口、加权总分 ≥85%。
7. 运行时已知缺陷全部修复：历史喂入、空 message 拦截、LLM 异常兜底、结构化输出解析兜底。

## 12. 里程碑与风险

| 里程碑 | 交付 |
|---|---|
| M1 训练数据构建 | §7 各能力数据集 + 标注规范 |
| M2 模型微调 | 五类能力微调模型 + §6 JSON 输出 |
| M3 运行时集成 | §8 改造 + §9 schema/表变更 |
| M4 评测验收 | §10 评估跑通，满足 §11 验收 |

**风险**：

- 编造风险（客服编造退款/电话是法律风险）——靠 §7 反例 + `must_not` + Go/No-Go 编造率 0 卡死。
- 训练数据量不足——五类能力样本需人工扩充，属最高工作量项。
- 结构化输出不稳定（JSON 偶发不合法）——靠 §8 解析兜底 + 纯文本回退。
- 2-gram 检索漏召回——由微调模型的槽位/意图能力兜底，检索仅作 FAQ 补充；必要时升级检索（§8.4）。
